## Working rules

- Work one bounded item at a time; record its source revision (commit, or base commit plus working-tree hashes), executed command and evidence before marking it verified.
- `Ready` means actionable, `Partial` means code exists but acceptance remains, `Intake` means historical requirements need current-code triage, and `Deferred` means intentionally outside the immediate sequence. No historical checkbox automatically becomes verified work.
- Evidence levels are distinct: unit, in-process integration, live lab, browser end-to-end, and operational pilot. Model forward passes and simulated traces do not prove trained-model performance or live provider results.
- Record completion here and update the state snapshot; do not create another sprint backlog. Historical IDs remain searchable in the crosswalk below.
- Operational device writes remain disabled by the development contract. Any later execution feature needs a separate authorized implementation scope and all execution gates below.

### BN-022 — Deferred security hardening (WP2.9 residuals, 20 November 2026)

Captured from the WP2.9 technical assessment of PR #17 @ `2b08851`
(merged as `9d08cc8`). These are **P2/P3 hardening items**, not merge
blockers; the owner accepted the two deployment restrictions below and
waived independent WP2.9 review for this merge. Implement in a
follow-up BN-022 hardening slice — do not implement inside the frozen
PR #17 branch.

1. **Cross-process JWT coherence.** `JwtKeyCache` is deliberately
   process-local (bounded TTL, fail-closed on read/parse/expiry,
   active-key-first rotation verification). Until a stronger
   invalidation mechanism exists, deployments are restricted to one
   Bonsai Core process per `bonsai_auth.db`. Active-active multi-process
   deployments sharing one AuthStore are unsupported; JWT rotation must
   be quiesced and every process restarted before auth resumes after an
   out-of-process key change.
2. **Authenticated backup manifests.** `bonsai backup` writes a
   SHA-256 manifest for integrity, but the manifest itself is
   unauthenticated and stored beside the snapshot — a writer who can
   modify the snapshot can regenerate it. Backup storage must be
   protected against unauthorized modification (same trust boundary as
   the live AuthStore: dedicated volume/host, restrictive perms,
   encryption at rest where available). Restores must follow
   `docs/auth_backup_restore_runbook.md`: verify manifests, perform
   emergency JWT rotation, reconcile, then install offline.

Additional nonblocking residuals already recorded in the BN-022 row:
outstanding JWTs of disabled users live until `exp`; process-wide AI
test `set_var`; Swagger self-hosting; CSPRNG audit for any remaining
non-auth secrets.

## Definition of done

A BN item closes only when its named acceptance is demonstrated at the required
evidence level, dependencies are satisfied, failure paths are checked, and the
support matrix is updated. Passing test counts, enum labels, UI builds and
historical “completed” tables alone do not close a live or operational gate.
