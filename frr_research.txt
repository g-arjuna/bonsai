BN-003: FRRouting VRF + BMP — Technical Root-Cause Investigation
1. Executive findings
The investigation has already uncovered a fundamental problem with the earlier implementation: the lab was expecting FRRouting to perform a Linux VRF provisioning operation that FRRouting explicitly says it does not perform.

The FRRouting 10.6 Zebra documentation states:
Zebra does not create Linux VRF.

This is documented under Virtual Routing and Forwarding in the official FRR manual. FRRouting

This changes how we should approach BN-003.
Initial conclusions
Question	Finding	Implication
Why was BLUE inactive?	The Linux VRF device was not provisioned.	FRR could not activate the configured VRF.
Was the BGP VRF syntax necessarily wrong?	No.	The inactive kernel VRF explains the observed Idle state without requiring a BGP syntax error.
Should Zebra create the VRF automatically?	No.	Provision the Linux VRF before expecting FRR to use it.
Is running Zebra as root the correct fix?	No.	It addresses the wrong responsibility.
Is FRR 10.6.1 inherently unsuitable?	Not established.	We need to examine BMP behavior before selecting a replacement.
Does VPNv4 automatically satisfy BN-003?	No.	An RD in VPNv4 NLRI is not equivalent to an RD in the BMP per-peer header.


The last distinction is particularly important.

BN-003 requires two independently verifiable properties:
1. A real BGP speaker produces BMP Route Monitoring messages for the route 10.99.1.0/24.
2. The corresponding BMP per-peer header identifies an RD-instance peer with the exact distinguisher 65000:100.
A successful BGP session, an active VRF, and even a correct VPNv4 route do not individually prove the second property.

The solution must explicitly validate the emitted BMP bytes, not merely confirm that FRR accepts the configuration.

2.1 The test provisions the kernel VRF explicitly
The upstream test_bgp_bmp_2.py runs:
tgen.net["r1vrf"].cmd(    """ip link add vrf1 type vrf table 10ip link set vrf1 upip link set r1vrf-eth1 master vrf1""")


It executes those commands before starting the FRR routing daemons.

That is the missing architectural step in the earlier BN-003 implementation.

The test then starts Zebra and BGP, explicitly loading BMP through:
router.load_frr_config(    config_path,    [        (TopoRouter.RD_ZEBRA, None),        (TopoRouter.RD_BGP, "-M bmp")    ],)


This is significant because BMP is a loadable FRR module. Enabling BMP configuration without loading the module is insufficient.
2.2 The reference uses rd vpn export, not merely vrf BLUE rd
The upstream router configuration includes:

The important command is:
rd vpn export 444:1

For BN-003, we need:
rd vpn export 65000:100

The BGP instance's export RD is directly relevant to how FRR constructs the BMP per-peer header.
2.3 FRR source code confirms the exact behavior
I inspected bgpd/bgp_bmp.c in the 10.6 branch.

Its bmp_get_peer_type_vrf() function distinguishes:
- Default VRF: peer type 0, global instance.
- Known non-default VRF: peer type 1, RD instance.
- Unknown VRF: peer type 2, local instance.
More importantly, bmp_get_peer_distinguisher() checks the configured IPv4 VPN export RD and copies its eight bytes into the BMP peer distinguisher.

Consequently, a recognized BLUE VRF with:
address-family ipv4 unicast
 rd vpn export 65000:100

has a source-code-supported path to producing the exact RD-instance peer header BN-003 requires.

That is much stronger evidence than assuming an RD configured somewhere in FRR will automatically reach BMP.
2.4 The upstream test actually validates RD changes
The test suite goes beyond checking BGP adjacency.

It changes an RD from 444:1 to 666:22 and checks that the collector receives corresponding BMP peer-down and peer-up events with the expected distinguishers.

This demonstrates that the desired functionality is already exercised by FRR's upstream tests.

It does not yet establish that your exact container image, startup sequence, and Bonsai collector work together. Those still require an end-to-end run.

3.2 Why the capability investigation went in the wrong direction
The image is not intended to give the unprivileged frr account unrestricted ability to create Linux networking devices.

Containerlab runs Linux nodes in privileged mode by default. Your observation that root can successfully execute ip link add ... type vrf already shows that the container's root context has the relevant permission. containerlab.dev

FRR's privilege framework also supports temporarily changing effective capabilities for operations that require them.

Therefore, an idle Zebra process showing CapEff=0 does not, by itself, establish a Zebra malfunction.

The previous attempts to modify file capabilities, daemon identity, and group membership were unnecessary for the required setup.

Regarding the daemon flags:
- -A sets the VTY listening address. It is not a supplementary-group option.
- -u sets the runtime user.
- I found no documented FRR 10.6 -G option that provides the proposed supplementary-group workaround.
The supported solution is to perform the small amount of kernel networking initialization as root and then let FRR start normally under its intended privilege model. FRRouting
3.3 One important containerlab detail
Containerlab's node-level exec commands run after container startup.

That means a simple configuration such as:
exec:
  - ip link add BLUE type vrf table 1001

does not guarantee that BLUE exists before FRR starts.

I recommend a pre-start wrapper using containerlab's documented cmd override:
1. Start the container with its existing tini entrypoint.
2. Wait until containerlab has created eth1 and eth2.
3. Create BLUE and attach eth2, as root.
4. Start FRR using the image's original /usr/lib/frr/docker-start.
This removes the VRF initialization race and does not require patching FRR or rebuilding the image. containerlab.dev

5. Does the VPNv4 workaround solve BN-003?
No—not the acceptance criterion you described.

FRR 10.6 supports the relevant commands:
address-family ipv4 vpn

and:
bmp monitor ipv4 vpn pre-policy
bmp monitor ipv4 vpn post-policy

These are the FRR command forms; address-family vpnv4 unicast and bmp monitor vpnv4 unicast are not the syntax used in its official 10.6 examples. FRRouting

However, there are two distinct places where an RD can appear.
Property	VPNv4 from a global BGP session	BLUE VRF BMP implementation
RD carried in VPNv4 NLRI	Yes, for VPNv4 routes	Not necessary
BMP peer type	0 — global instance	1 — RD instance
BMP peer distinguisher	Zero	65000:100
Route Monitoring payload	MP_REACH/MP_UNREACH VPNv4 data	IPv4-unicast BGP UPDATE
Meets the requested BN-003 proof	No	Yes, if live verification passes


FRR's source establishes the critical distinction: the BMP peer type comes from the monitored BGP instance's VRF ID, not from the address family of the BGP UPDATE.

For a default-instance peer, the BMP distinguisher is zero even when the UPDATE contains VPNv4 NLRI with its own RD.

That behavior is consistent with RFC 7854's distinction between global-instance and RD-instance BMP peers. RFC Editor

6. Precisely how to prove the corrected configuration works
This is the most important operational part.

A green containerlab deployment is not enough. An Established BGP session is not enough. Even a route appearing in FRR's BLUE RIB is not enough.

We want proof from actual transmitted BMP bytes.
Step 1: Extract the lab
Copy the downloaded ZIP to the Ubuntu machine, then:
cd /home/arjuna/Desktop/bonsai/lab/fast-iteration

unzip bn003-frr-bmp-vrf-repro.zip

cd bn003-frr-bmp-vrf

Step 2: Run the independent BMP collector
In terminal 1:
python3 verify_bmp.py --seconds 120

This opens a genuine TCP listener on port 11029.

It does not create synthetic frames. It reads what FRR sends across the TCP connection.

Do not run it at the same time as Bonsai's own BMP listener on that port.
Step 3: Deploy FRR
In terminal 2:
sudo containerlab deploy -t frr-bmp-vrf.clab.yml

Inspect the VRF and BGP state:
sudo docker exec clab-bonsai-bn003-vrf-frr1 \
  vtysh -c 'show vrf'

sudo docker exec clab-bonsai-bn003-vrf-frr1 \
  vtysh -c 'show bgp vrf BLUE ipv4 unicast summary'

sudo docker exec clab-bonsai-bn003-vrf-frr1 \
  vtysh -c 'show bgp vrf BLUE ipv4 unicast 10.99.1.0/24'

The expected result is an active BLUE VRF, an Established BLUE BGP adjacency, and the prefix 10.99.1.0/24 received from frr2.
Step 4: Examine the BMP wire proof
The supplied Python collector checks for both of these events:

BMP Peer Up
BMP version:         3
BMP message type:    3 (Peer Up)
BMP peer type:       1 (RD instance)
Peer distinguisher:  65000:100

BMP Route Monitoring
BMP version:         3
BMP message type:    0 (Route Monitoring)
BMP peer type:       1 (RD instance)
Peer distinguisher:  65000:100
BGP message type:    2 (UPDATE)
Advertised NLRI:    10.99.1.0/24

For this ASN-based RD, the eight-byte distinguisher must be:
00 00 fd e8 00 00 00 64

The BMP common header occupies the first six bytes. The peer-type byte is at offset 6, and the eight-byte peer distinguisher occupies offsets 8–15.

These offsets are defined by the BMPv3 common and per-peer header layouts in RFC 7854. RFC Editor

The probe records the raw frames in genuine-bmp-stream.bin, giving you evidence that can be inspected independently.
Step 5: Only then integrate Bonsai
Once the raw wire test passes, stop the standalone collector and start Bonsai's real BMP listener.

Check the listening address carefully.

If Bonsai listens only on:
127.0.0.1:11029

the FRR container cannot reach that socket through the Docker management bridge.

Bonsai must listen on an address reachable from the container, such as:
0.0.0.0:11029

or the management bridge address:
172.100.208.1:11029

Restart or reconnect the BMP exporter so Bonsai receives a fresh peer-up and initial route synchronization.

At that point, the final BN-003 assertion should verify that Bonsai populated the expected VRF-scoped RIB using the actual received BMP stream.
7. What the coding tool failed to do
My assessment is that the previous attempt had four identifiable shortcomings.
Failure	Why it mattered	Corrected approach
Expected Zebra to create BLUE	FRR doesn't create Linux VRFs	Provision BLUE through Linux before starting FRR
Focused on Zebra privileges	FRR daemon identity was not the underlying provisioning requirement	Use the container's existing root startup context
Used an insufficiently established RD configuration	A VRF declaration alone doesn't prove that BMP uses 65000:100	Configure rd vpn export 65000:100, matching FRR's upstream test
Relied on local prefix origination	Could produce Loc-RIB observations without proving a monitored RD-instance neighbor update	Have frr2 advertise the prefix and frr1 receive it


The distinction between a locally originated route and an inbound BGP UPDATE is particularly important.

FRR's BMP implementation uses peer type 3 for Loc-RIB monitoring, while a normal BGP neighbor in an active non-default VRF produces peer type 1.

BN-003 should not accidentally accept the former as proof of the latter. FRRouting
One additional finding: 10.6.1 was not necessarily the problem
I compared the BMP peer-type and RD-distinguisher implementation at the exact FRR 10.6.1 and 10.6.2 release tags.

The relevant source code is identical in those two releases.

This means the recommendation to move to 10.6.2 is for a maintained patch version, not because 10.6.1 lacked the required capability.

The previous lab most likely failed because of its VRF provisioning and RD-export configuration, not because the feature was absent from FRR 10.6.1.

For BN-003, I would make this the reference implementation:

FRR 10.6.2 → Linux VRF BLUE provisioned before FRR startup → eBGP prefix received inside BLUE → BMP peer type 1 with RD 65000:100 → Bonsai VRF-scoped RIB.
