## Phase 0 — Clean-Slate Reset & Pre-Flight

> **Do this every time you start a new EV1 test run.** Stale WAL files, a lingering bonsai
> process, or a half-deployed clab lab are the #1 cause of getting stuck in Phase 1–2.
> Follow every step in order. Do not skip.

### 0.1 — Kill any running bonsai or sidecar processes

```bash
# Kill bonsai core (binds :3000, :50051, :50052, :5514, :9162)
pkill -f "target/release/bonsai" 2>/dev/null || true
pkill -f "bonsai --config"       2>/dev/null || true

# Kill Python sidecar (collector_engine.py, binds :9200, :9201)
pkill -f "collector_engine.py"   2>/dev/null || true
pkill -f "bonsai_agent"          2>/dev/null || true

# Confirm nothing is holding the ports
sleep 2
ss -tlnp | grep -E "3000|9200|50051|50052|5514|9162" || echo "All ports free"
# Expected: no output (all ports free)
```

- [ ] `ss` output is empty — no stale process owns any port

### 0.2 — Wipe the database and WAL files

> **Why**: lbug (the embedded graph DB) uses a WAL (Write-Ahead Log). A crashed or
> interrupted bonsai process leaves a partial WAL that causes `LOCK` errors or silent
> data corruption on the next start. Always wipe on a clean-slate run.

```bash
cd ~/bonsai

# Full wipe: DB file + WAL + parquet exports + vault
rm -rf runtime/
# This removes:
#   runtime/bonsai.db          — lbug main database
#   runtime/bonsai.db-wal      — WAL (the silent killer)
#   runtime/bonsai.db-shm      — shared memory file
#   runtime/vault/             — encrypted vault (passphrase re-initialises it)
#   runtime/parquet/           — parquet exports (re-generated by sidecar)
#   runtime/models/            — saved GNN model checkpoints
#   runtime/tls/               — will be re-populated in step 1.2

# Confirm clean
ls runtime/ 2>/dev/null && echo "WARNING: runtime/ still exists" || echo "Clean"
```

- [ ] `runtime/` directory does not exist

> **If you want to preserve a previous DB** (resuming, not clean-slate): skip `rm -rf runtime/`
> but still do `rm -f runtime/bonsai.db-wal runtime/bonsai.db-shm` to clear any stale WAL.

### 0.3 — Tear down and redeploy the ContainerLab

> Reusing a lab from a previous run can leave stale gNMI TLS certs, half-configured
> BGP sessions, or a missing clab CA. Always redeploy for a clean run.

```bash
cd ~/bonsai/lab/fast-iteration

# Tear down if already running (safe to run even if lab is not up)
sudo clab destroy -t 3node-srl.clab.yml --cleanup 2>/dev/null || true

# Wait for containers to fully stop
sleep 5
docker ps | grep clab || echo "No clab containers running"

# Redeploy
sudo clab deploy -t 3node-srl.clab.yml
# Expected: "container started" for srl1, srl2, srl3

cd ~/bonsai
```

- [ ] `clab deploy` completes without error
- [ ] `docker ps` shows 3 containers: `clab-bonsai-srl-srl1`, `clab-bonsai-srl-srl2`, `clab-bonsai-srl-srl3`

Wait 30 seconds for SRL to boot, then verify:
```bash
ping -c1 -W2 172.100.100.11 && ping -c1 -W2 172.100.100.12 && ping -c1 -W2 172.100.100.13
ssh -o StrictHostKeyChecking=no -o ConnectTimeout=5 admin@172.100.100.11 \
    'show version | grep "SRL"' 2>&1 | head -3
# Expected: SRL version line printed
```

- [ ] All 3 pings succeed
- [ ] SSH to srl1 works and prints version

### 0.7 — Locate the clab CA certificate

> ContainerLab auto-generates a CA for each lab. Its location depends on clab version
> and where you ran `clab deploy`. Check both candidates:

```bash
# Candidate 1: user home (clab >= 0.40 default)
ls ~/.clab/certs/bonsai-srl/ca/ca.pem 2>/dev/null && \
  echo "CA found at ~/.clab/certs/bonsai-srl/ca/ca.pem"

# Candidate 2: alongside the topology file (older clab or sudo deploy)
ls ~/bonsai/lab/fast-iteration/clab-bonsai-srl/ca/ca.pem 2>/dev/null && \
  echo "CA found at lab/fast-iteration/clab-bonsai-srl/ca/ca.pem"

# Candidate 3: search
sudo find /root /home -name "ca.pem" 2>/dev/null | grep bonsai

# Once found, set the variable:
export CLAB_CA="<path-from-above>"
# e.g. export CLAB_CA="$HOME/.clab/certs/bonsai-srl/ca/ca.pem"

# Validate
openssl x509 -in "$CLAB_CA" -noout -subject -dates
# Expected: subject=CN=bonsai-srl  notAfter=<future date>
```

```bash
# Copy into runtime/tls/ so bonsai.toml can reference it with a relative path
mkdir -p ~/bonsai/runtime/tls
cp "$CLAB_CA" ~/bonsai/runtime/tls/clab-ca.pem

# Verify the cert covers the nodes (SAN check)
openssl x509 -in ~/bonsai/runtime/tls/clab-ca.pem -noout -text \
  | grep -A3 "Subject Alternative"
# Note the CN/SAN values — you need the exact string for tls_domain in bonsai.toml
# Common values: "srl1" or "clab-bonsai-srl-srl1"
```

```bash

  -servername srl1 </dev/null 2>&1 | grep -E "Verify return|CN="
# Expected: Verify return code: 0 (ok)
# If "CN=clab-bonsai-srl-srl1" appears → use tls_domain = "clab-bonsai-srl-srl1"
# If "CN=srl1" appears              → use tls_domain = "srl1"
```

## Phase 2 — Device Onboarding

### 2.0 — Why two steps: bootstrap then register

Bootstrap (SSH/CLI) and gNMI subscription are separate:

1. **Bootstrap** (paramiko SSH) — reads topology via SRL CLI, seeds the graph with interfaces/BGP/LLDP
2. **Register as managed device** — tells Bonsai to open a gNMI subscription for live telemetry
3. **Assign gNMI path profile** — selects which gNMI paths to subscribe (counter rates, BGP state, etc.)

All three happen in sequence below. Skipping any step causes partial data or missing telemetry.

### 2.1 — Bootstrap srl1 (SSH-based, paramiko)

```bash
# Bootstrap srl1 — uses paramiko SSH (NOT PyATS — SRL has no PyATS/Unicon plugin)
curl -s -X POST http://localhost:3000/api/devices/bootstrap \
  -H 'Content-Type: application/json' \
  -d '{
    "address":          "172.100.100.11",
    "credential_alias": "srl-lab",
    "vendor":           "nokia_srlinux"
  }' | python3 -m json.tool
```

**Expected response (success):**
```json
{
  "status": "ok",
  "address": "172.100.100.11",
  "hostname": "srl1",
  "vendor": "nokia_srl",
  "interfaces_seeded": 4,
  "bgp_neighbors_seeded": 2,
  "lldp_neighbors_seeded": 2,
  "elapsed_s": 12.4
}
```

**If you get `"status": "failed"` with SSH error:**
- Verify SSH works manually: `ssh admin@172.100.100.11` (password: `NokiaSrl1!`)
- Confirm the credential alias was saved: `curl -s http://localhost:3000/api/credentials`
- Check bonsai log: `tail -50 runtime/bonsai.log`

**If you get `"status": "partial"` with SRL learn errors:**
- SRL CLI JSON output parsing can fail if the SRL image version changed the path names
- Check `runtime/bonsai.log` for `"SRL interface learn failed"` lines
- Partial result is still useful — interfaces may be missing but BGP/LLDP still seeded
- Continue to 2.2 and fix seed manually if needed

**Verify graph seeded correctly:**
```cypher
MATCH (d:Device {address: "172.100.100.11"})-[:HAS_INTERFACE]->(i:Interface)
RETURN i.id, i.name, i.oper_status, i.admin_status
```
- [ ] Interfaces show `id = "172.100.100.11:ethernet-1/X"` (the `id` field is critical for gNMI dedupe — see note below)
- [ ] `oper_status` populated from CLI state

> **Interface down storm fix**: The bootstrap seed now writes `i.id = "address:name"` matching
> the gNMI subscriber's key. This prevents the first gNMI poll from firing `interface_down`
> for every interface that was already `down` at bootstrap time (false-positive storm). If you
> are testing on an older build without this fix, expect a burst of `interface_down` detections
> ~30s after gNMI subscription starts — they are all false positives from the initial state sync.

```bash
    "hostname":         "srl1",
    "vendor":           "nokia_srlinux",
    "role":             "spine",
```

> **Address normalisation (fixed)**: The bootstrap API accepts **either** form — bare IP
> `172.100.100.11` or full `172.100.100.11:57400`. The agent automatically appends `:57400` if

> used for gNMI subscriptions. **Do not pass the bare IP** — always pass `172.100.100.11:57400`
> to be explicit and avoid any edge case.
>
> **Duplicate device guard**: In older builds the bootstrap could create a second bare-IP managed
> device alongside the intended `:57400` entry. This is fixed. If you see a duplicate bare-IP
> entry after bootstrap, remove it:
> ```bash

>   -H 'Content-Type: application/json' \
>   -d '{"address": "172.100.100.11"}'

> # Confirm only :57400 entries remain:
> curl -s http://localhost:3000/api/onboarding/devices | python3 -c \
>   "import sys,json; [print(d['address']) for d in json.load(sys.stdin).get('devices',[])]"
> ```

```bash
nc -zv 172.100.100.11 57400

# Step 5: check bonsai logs for the exact gRPC error

```

- [ ] `blockers: []` — no missing subscription paths

### 2.5 — Assign gNMI path profile

The path profile controls which gNMI paths Bonsai subscribes to.

> **Route clarification**: `PATCH /api/devices/{address}/profile` is now wired and works.
> It delegates to the same handler as `POST /api/devices/{address}/selected-paths`.
> Both are equivalent — use whichever feels natural.

```bash
# srl1 = spine role → dc_spine profile
curl -s -X PATCH http://localhost:3000/api/devices/172.100.100.11%3A57400/profile \
  -H 'Content-Type: application/json' \
  -d '{"profile": "dc_spine"}' | python3 -m json.tool

# srl2 and srl3 = leaf role → dc_leaf profile
for PORT_ADDR in 172.100.100.12%3A57400 172.100.100.13%3A57400; do
```

```bash
import torch

loss_fn = FocalControlWeightedLoss(gamma=2.0)
logits = torch.tensor([[0.1, 0.9], [0.8, 0.2]])  # 2 samples
labels = torch.tensor([1, 0])  # fault, normal
change_weights = torch.tensor([0.0, 1.0])  # first sample in change window

loss = loss_fn(logits, labels, change_weights)
print(f'CW loss: {loss.item():.4f}')

loss_no_cw = loss_fn(logits, labels, torch.ones(2))
print(f'No-CW loss: {loss_no_cw.item():.4f}')
```
