# BN-021c — Real-TCP Shared-NAT BMP Acceptance Evidence

Date: 2026-11-10/11 (UTC). Branch: `feat/bn021c-bmp-exporter-isolation`.
Routing binary: `target/debug/bonsai-routing` built from this branch,
packaged as local image `bn021c-routing:local`.

## Topology

Dedicated Docker bridge networks only (`bn021c-*` names); no production or
unrelated container networking was touched. Reproduce with
`lab/acceptance/bn021c-nat/up.sh` (all commands are in that script).

```text
                 bn021c-peer (10.240.0.50, AS 65000, route-server)
                          ^  eBGP
   frr-a ─┐                |                ┌─ frr-b      (site subnets
   10.240.1.11/24         |                |  10.240.2.0/24)
          ├─> bn021c-nat ─┼──> bn021c-bonsai (10.240.0.20:11019 BMP,
   frr-c ─┘  iptables     |     10.240.0.200 SNAT for ALL BMP
   10.240.3.13/24  SNAT   |     10.240.0.20x per-site SNAT for BGP)
                          v
                    10.240.0.0/24 (public)
```

NAT proof (`runtime/nat-rules.txt`): three site subnets SNAT all TCP/11019
traffic to the single address `10.240.0.200`. BGP (TCP/179) uses per-site
translations `10.240.0.201/.202/.203` so the route-server sees three
distinct neighbors. Every BMP speaker observed by Bonsai therefore has
`speaker_addr = 10.240.0.200` — the same translated source IP.

Exporters: FRR 10.6.1 (`quay.io/frrouting/frr:10.6.1`), AS 65001/65002/65003,
each with `bmp connect 10.240.0.20 port 11019` monitoring
pre-policy/post-policy/loc-rib IPv4 unicast. The peer originates
`10.99.0.0/24` plus per-exporter prefixes (`203.0.113.0/24` via A,
`198.18.0.0/24` via B, `192.0.2.0/24` via C), so every exporter sees the
same overlapping peer address `10.240.0.50`.

Identity DB (`runtime/bonsai_config.db`, generated by
`lab/acceptance/bn021c-nat/make_identity_db.py`) binds sysName claims:
`frr-a -> exp-frr-a -> dev-frr-a`, `frr-b -> exp-frr-b -> dev-frr-b`.
`frr-c`/`frr-d` are intentionally unbound.

## Scenario results

### A — Distinct trusted exporters behind one NAT source — PASS

`api/01-speakers-baseline.json`: three speakers, all with
`speaker_addr = "10.240.0.200"`:

| speaker_key                              | exporter_instance       | device_id   | identity   | epoch | routes |
|------------------------------------------|-------------------------|-------------|------------|-------|--------|
| 10.240.0.200\|exp:exp-frr-a             | exp:exp-frr-a           | dev-frr-a   | resolved   | 1→6  | 4      |
| 10.240.0.200\|exp:exp-frr-b             | exp:exp-frr-b           | dev-frr-b   | resolved   | 2→8  | 4      |
| 10.240.0.200\|conn:803f0d…/conn:2bf9…    | conn:*                  | null        | provisional| 5/7   | 2      |

Route isolation (`api/02-*`): A sees `203.0.113.0/24`, B sees
`198.18.0.0/24`, both see shared `10.99.0.0/24` — selected per
`exporter_instance`. Peer listing (`api/03-peers.json`) shows the same
peer IP `10.240.0.50` under distinct exporter instances.

### B — Withdrawal isolation — PASS

Withdrew `203.0.113.0/24` at the route-server (`no network`).
`api/04/05`: A lost only that prefix; B retained `198.18.0.0/24` and
`10.99.0.0/24`. No cross-exporter mutation.

### C — PeerDown isolation — PASS

`neighbor 10.240.0.50 shutdown` on frr-a. `api/06/07/08`: A's peer went
`down`; B's peers stayed `up` and B's routes were unchanged.

### D — Disconnect and reconnect — PASS

`docker stop bn021c-frr-a` → `api/09`: speaker
`10.240.0.200|exp:exp-frr-a` entered `completeness_state = gap` with
`transport_gap.reason = bmp_tcp_eof`, session_epoch 1, last-known 4 routes
retained (no fabricated withdrawals). B and the conn:* speaker were
unaffected (`api/10`). After `docker start`, frr-a reconnected under the
same exporter scope as session_epoch 4, gap cleared, routes repopulated
(`api/13/14`).

Note: exporter containers must have their default route pointed at their
site NAT gateway (`10.240.x.2`); Docker's bridge default via `.1` does not
reach the public network. `up.sh` applies this at bring-up; after a manual
container restart re-apply `ip route replace default via 10.240.x.2`
(FRR staticd also installs the route but the kernel prefers the Docker
one). This is a lab-topology detail, not a product defect.

### E — Unknown exporter — PASS

Unbound exporter (originally `frr-c`, later `frr-d`) resolves to
`conn:<id>` with `identity_status = provisional`,
`device_id = null`, `exporter_id = bmp:<sysName>`. It never acquires an
authoritative device association (`api/18-speakers-final.json`).

### F — Conflicting / indistinguishable identity claims — CONFIRMED LIMITATION

Recreated the site-C exporter with `--hostname frr-a` while the real frr-a
was still connected. Bonsai resolved the new connection to the same
`exp:exp-frr-a` scope and merged its state: `total_routes` went 4→6 and
`192.0.2.0/24` (the impostor's prefix) appeared in A's route list
(`api/15/16/17`). The peer list shows the impostor's Loc-Rib peer
(`0.0.0.0`, peer_as 65003) folded into the same speaker.

This is the documented trust assumption: a BMP `sysName` is a
self-reported claim, not authenticated identity. Two exporters presenting
the same claim behind the same NAT source are indistinguishable and
coalesce. Operators must treat trusted sysName bindings as an
administrative mapping provisioned out-of-band; reliable disambiguation
requires a future authenticated-ingress mechanism (deferred). Unbound or
ambiguous claims fail closed into per-connection `conn:*` isolation.

### G — Restart and replay — PASS (BN-005 contract preserved)

Pre-kill snapshot: `replay/speakers-pre-kill.json`
- `exp:exp-frr-a` epoch 4, complete, 6 routes (A + earlier impersonator)
- `conn:803f…` epoch 5, syncing, 2 routes (live unbound exporter)
- `exp:exp-frr-b` epoch 2, gap, 4 routes (recorded `bmp_tcp_eof` disconnect)

Abrupt kill: `docker kill --signal=KILL bn021c-bonsai` (SIGKILL — no
disconnect records could be written for live sessions), then
`docker start`. Journal/event logs at kill time: 165 BMP journal records,
162 event records.

Post-restart (`replay/speakers-post-restart.json`,
`replay/speakers-very-final.json`):

- `exp:exp-frr-b` epoch 2 **gap, 4 routes** — the recorded clean
  disconnect and last-known routes survived replay exactly. No fabricated
  withdrawals.
- `conn:803f…` epoch 5 **syncing, 2 routes** — replayed as last-known
  state with no disconnect record. This is the intended BN-005 semantics:
  absence of a durable disconnect does not prove the connection is dead,
  and replay must not fabricate one. (Operational limitation: the stale
  `conn:*` speaker remains visible until its exporter reconnects under a
  new connection-scoped identity or an operator reconciles it.)
- `exp:exp-frr-a` epoch 6 and `conn:2bf9…` epoch 7 — exporters reconnected
  with fresh session epochs; old-epoch payloads are fenced.
- Journals appended durably across restart (223 journal records,
  220 event records at end of run).

## API / graph attribution

- `/internal/routing/v1/speakers|peers|routes` honor
  `exporter_instance` and exact `speaker=addr|instance` selectors; bare
  `speaker=10.240.0.200` still matches all logical exporters on that
  address (legacy-compatible).
- Event journal `event_key.source` carries `collector_id`,
  `exporter_id`, `exporter_addr`, `exporter_instance`, `session_epoch`,
  `device_id` per event (`runtime/events.jsonl`), so graph/projection
  attribution never collapses NAT-sharers: `speaker_projection_id()`
  yields `10.240.0.200|exp:exp-frr-a` etc., and `TelemetryUpdate.target`
  uses that scoped id.
- `/internal/routing/v1/coverage` reports family support states;
  unresolved exporters carry no `device_id`.

## Confirmed defects corrected during hardening (covered by
`tests/bn021c_exporter_isolation.rs`, 12 tests)

- P0-A: exporter scope now encodes the identity namespace
  (`exp:{scope}:{canonical}` for non-default scopes; `exp:{canonical}`
  preserves legacy default-scope journal compatibility) and
  `RoutingServiceConfig.identity_scope` makes the ingress scope explicit.
- P0-B: malformed BMP frames now record a distinct
  `bmp_frame_rejected:*`/transport-error disconnect and still run
  conn-scope retirement — verified over real TCP in the loopback test.
- P0-C: BMP Termination is deferred per sending connection; it retires
  only that connection's session and cannot remove sibling state.
- P0-D: ambiguous/conflicting claims fail closed into `conn:*`
  isolation; only `Resolved` bindings produce `exp:*`/`device_id`.
- P1: routing service opens the identity DB read-only
  (`SqliteStore::open_file_readonly`) — no schema migration or WAL
  mutation from the routing path.

## Remaining limitations

- sysName-based coalescing (Scenario F) is a trust assumption, not
  authentication; ingress-authenticated exporter identity is future work.
- `conn:*` speakers replayed without a disconnect record retain
  last-known state indefinitely (BN-005 contract); distinguishing dead
  vs. silently-alive unclean connections is not possible from the journal
  alone.
- Exporter container restarts need the site-default-route fix described
  above (lab topology only).
- Production acceptance additionally requires deployment-specific ingress
  authentication and operational runbooks (BN-021f scope).
