# 2026 Bonsai UI, environment onboarding, topology trust and product comparison

**Review date:** 11 November 2026  
**Source baseline:** `main` at `50ba09bd352d7471ff996a95b67f6532bbeca371` (PR #3 merged).  
**Method and boundaries:** static read of the Svelte application, the onboarding/site/device/topology APIs, discovery/profile resolver, selected regression tests and existing SuzieQ-versus-PyATS ADR; research against publicly documented product capabilities. No browser session against a deployed Bonsai, packet capture, NetBox/ServiceNow account, accessibility scan, pen test or performance test was executed. Findings below are source-supported risks, not live failure claims. Current NetFlow changes remain untouched.

## Executive recommendation

**Do not rewrite the UI. Fix its truth contract and organize its existing workspaces around a durable environment → asset → observation → evidence → investigation journey.** The graph must never silently turn an inventory record, a device capability advertisement, an unresolved BGP address, a one-sided LLDP neighbor or an external CMDB assertion into a verified physical connection. The UI must work whether the deployment has **no external inventory**, NetBox/Nautobot as an intended-state authority, ServiceNow CMDB as business/ownership context, or both.

The existing UI is extensive: authentication, first-run onboarding, devices, physical/site hierarchy, environments, gNMI profiles, credentials, collectors, routing/RIB, Live topology, incidents/investigations, graph Explorer, approvals, integrations, sidecars, stream controls, audit/HA and operational settings. It is not necessary to replace those components. What is missing is a consistent cross-workspace identity, lifecycle, capability, hierarchy and evidence contract.

**Highest priority:** three static, reproducible **code-path contradictions** must be turned into failing-then-passing tests before promoting the topology as trustworthy:

1. **NetBox import cannot finish through the current selected-device path.** `ui/src/lib/Onboarding.svelte:421-449` POSTs `selected_paths: []` to `/api/onboarding/devices/with_paths`. `src/http_server/managed_devices.rs:245-255` rejects an empty plan. The preview may succeed while every selected import fails. This is a cross-file code-confirmed contract mismatch, not live NetBox acceptance.
2. **Saving a device can reset an existing site hierarchy.** `src/http_server/managed_devices.rs:320-325` invokes `sync_sites_from_targets`; `src/graph/mod.rs:2654-2673` synthesizes a root `SiteRecord` with name-derived ID, empty parent, kind `unknown`, zero coordinates and empty environment; `upsert_site_record:9226-9237` updates the site's parent, kind, lat/lon and metadata on a match. A legitimate site whose ID is the name-derived slug can lose its metadata/hierarchy when its device is updated. This is far more serious than a UI tree rendering issue; assert metadata invariants server-side.
3. **The topology API may attach a BGP session to the wrong peer device.** `src/http_server/observability.rs:253-266` finds the first BGP_SESSION_WITH destination from the source where `dst == peer || allowed_devices.contains(dst)`. The second condition is true for any onboarded destination, not necessarily the session's peer. With two BGP sessions, the wrong destination can be selected. A displayed L3 edge can therefore be unsound even though the observed BGP session itself is real. Require exact identity-aware session-peer linkage.

Other critical risks are documented below, including non-gNMI onboarding, site-name collisions, incomplete discovery, topology inventory omission and misleading “healthy”/“path” semantics.

## A. UI information architecture and entity contract

### A1. Concepts operators should see, not conflate

| Concept | Definition / safe key | UI behavior |
|---|---|---|
| **Environment** | Operational archetype and collection/security policy (`data_center`, `service_provider`, campus, cloud, mixed); not necessarily geographic | May span sites; holds policy and supported-source profiles. Changing it must not silently reassign devices or collectors. |
| **Site** | Physical/geographical or deployment grouping with immutable site ID and optional parent; region → DC/PoP → building/pod/row → rack | Show even if empty; use ID, not name, in selectors and scoped queries. A site name may repeat under different parents. |
| **Tenant / VRF / routing instance** | Orthogonal logical scoping; RD/RT/VNI/namespace do not define physical site | One device may carry several logical tenants; do not apply a single “site” filter as tenant isolation. |
| **Asset (known/managed)** | Inventory-backed or manually declared device, even when unreachable, disabled, offline or unsupported | Visible in Inventory/Topology with **inventory-only** badge; no inferred physical links without observations. |
| **Observed device/source** | Collection view authenticated or not, source/collector/transport, per-protocol capability | A source alias is not canonical device identity. Unresolved/quarantined evidence displayed separately; never auto-merge on IP alone. |
| **Topology edge** | Evidence-backed typed L1/L2/IGP/BGP/VPN/overlay/forwarding/service relation with direction, source, as-of and confidence | Distinguish **observed bidirectional**, **observed unilateral**, **inferred**, **declared**, **conflicted**, **stale**, **unavailable**; make click-through evidence mandatory. |
| **Operational state** | Healthy/degraded/down/unknown/unsupported/not-collected/stale, scoped to a particular facet and time | Never interpret missing telemetry, unsupported protocol or old datapoints as healthy/empty/zero. |
| **Source of truth** | Per-field or domain authority: Bonsai-managed, NetBox/Nautobot intention, ServiceNow ownership, device operational observation | Reconciliation produces “accepted / ignored / conflict / suggested edit” with provenance, not blind overwrite. |

**Recommended stable default workflow:** `Environments` (select/create source and scope) → `Sites` (optional hierarchy) → `Inventory` (manual/CSV/NetBox/Nautobot/CMDB) → `Capabilities & Collection` (per-device protocol probes, select safe plan) → `Observation health` (per source and epoch) → `Live topology` (layered and explicitly incomplete) → `Investigate` (as-of evidence) → `Operations` (review and assurance). Reuse existing routes as steps with deep links; no ten-step mandatory ceremony for a single device.

### A2. Three onboarding modes supported by one consistent UX

1. **Standalone/no integrations:** CSV/JSON/manual device import works without external CMDB, and accepts offline/unsupported/partial devices as **inventory-only**. Display which protocols can be tried (gNMI, SNMP poll/trap, SSH/CLI, BMP from active exports, syslog, NetFlow/sFlow, controller API) as optional collection methods. The UI must not require gNMI or “at least one subscription path” to register a legitimate device. Enforce method-specific authorization and testing only when enabling that collector. Never pretend passive BMP/syslog proves full device inventory.
2. **NetBox/Nautobot authoritative for intended DCIM/IPAM:** show preview, immutable external object ID, site hierarchy/tenant/VRF/role, overlaps, no primary IP, disabled/decommissioned devices, duplicates, changed names/addresses, supported vendor/platform profile, desired versus observed differences. Import transactionally or as a durable job with per-row replayable outcomes. No automatic rewriting of authoritative NetBox/CMDB from Bonsai without explicit reverse-sync scope. Use secrets aliases, not a copied arbitrary first credential.
3. **ServiceNow CMDB optional:** adopt service ownership, configuration item and change/incident relationships **without** requiring CMDB for topology; show exact reconciliation source, class mapping, freshness, duplicate CI conflicts, missing CI and authoritative-field rules. Store CMDB relation separately from proven network adjacency. Both NetBox and ServiceNow may connect; conflicting values show both assertions and an explicit resolution, never silent last-write-wins.

**Per-device capability matrix:** columns for protocol/transport, vendor/version/feature, `supported` vs `advertised`, probe result, active subscription/CLI job, last good observation, per-path data availability, parser coverage and graph projection; rows for LLDP/CDP, interface & optics, BGP BMP vs BGP gNMI/CLI, IS-IS/OSPF/BFD, VPN/EVPN/VXLAN, FIB/LFIB/labels, SNMP, syslog, flows/OTLP. States: `not attempted`, `unsupported`, `supported but disabled`, `auth/TLS failure`, `rate-limited`, `reachable no data`, `receiving`, `stale`, `conflicting`. A `gNMI Capabilities` success means only that the RPC returned, not that route views and graph paths were validated.

**Lifecycle:** `declared` → `probe planned` → `reachable` → `collecting` → `observed` → `reconciled` → `validated`, with independent `disabled`/`offline`/`unsupported`/`gap` states per source, not a single magic health color. Running protocol probes may fail; non-gNMI devices remain onboarded and useful for coverage/intent/incident search.

### A3. Geography and topology rules

- Sites are **catalogued** from the site repository, not inferred only from observed `Device.site` strings. Show empty sites, orphaned assets, split-brain names, sites with no graph data and device count `known / observed / validated`. Map geography optionally from verified coordinates; do not invent lat/lon from a `0,0` default.
- Site selection includes its descendants by **site ID** with breadcrumbs and an explicit “include sub-sites” choice. Edge crossings are visible as **off-site stubs** rather than silently deleted. “DC”, “fabric”, “pod”, “rack”, “region”, “PoP”, “campus”, “cloud region” are different grouping kinds, not topology facts or a single mandatory tree hierarchy.
- Physical/LLDP and management connectivity remain distinct. A BGP adjacency does not imply a direct cable; an EVPN control route does not establish a working VTEP; a P-router underlay hop may be absent from BMP, not absent from the network.
- A device that is registered but never seen is drawn as `inventory only` in a list/ghost layer and excluded from verified-path computation. A stale link has an age and observed/unobserved interval; unknown/absent must not be conflated.
- Save stable layout per user/environment/scope; cluster and progressively render site/fabric/pod for >1k nodes; table/keyboard alternatives and accessible descriptions; provide discoverable as-of time and source coverage.
- Topology overlays should be switchable between **inventory/intent**, **physical**, **IGP underlay**, **BGP control**, **VPN/EVPN**, **forwarding** and **services/impact** with mutually exclusive legends and typed, evidence-linked paths. Never display a graph-estimated shortest path as a proven forwarding path.

## D. Product comparison: learn, integrate, and avoid reimplementing

This comparison is **capability positioning from official documentation**, not a controlled performance benchmark or a claim Bonsai currently outperforms products. Verify licenses/versions before any embedding or use of third-party collectors.

| Product / established capability | Existing strength / experience to learn from | Reuse / integration choice for Bonsai | Distinct Bonsai proof to target |
|---|---|---|---|
| **SuzieQ (OSS)** | Multi-NOS agentless SSH/REST collection, normalized tables for device/interfaces/LLDP/MAC/ARP/routing/BGP/OSPF/EVPN-VNI; time-aware queries, `assert`, path and namespace semantics. | **Do not write another generalized CLI-polling database** merely to catch up. Retain existing PyATS/Genie/TextFSM ADR, evaluate an *optional* SuzieQ read adapter for device snapshots and a comparative benchmark; don't make SuzieQ a hard dependency or duplicate its credentials/config database. | Bonsai's streaming BMP/gNMI plus journal replay, provenance-scoped graph and curated LLMops have to **demonstrate** improvements in freshness, trust and corroborated diagnosis. |
| **NetBox / NetBox Discovery** | Durable intended DCIM/IPAM, sites/regions, VLANs/VRFs, cables/circuits, tenant context; current discovery integrations can populate NetBox. | Prefer NetBox as authoritative intended inventory when installed. Import by external immutable ID with diff/conflict; no Bonsai clone of racks, cabling, IPAM or change journals. A standalone local minimal asset registry is still essential without NetBox. | Reconcile intended vs observed network topology/forwarding with evidence and unknowns, without corrupting NetBox intentions. |
| **Nautobot** | Extensible source-of-truth, network jobs, onboarding/SSoT and integration ecosystem. | Optional SSoT adapter using common importer contract, not a second embedded source-of-truth platform. Evaluate app API versions and field map; prefer adoption of its validated data models. | Flexible plug-in intake + deterministic observational validation into graph/agent tools. |
| **IP Fabric (commercial)** | Network discovery/snapshots, configuration and connectivity models, assurance, historical diff, path simulation, UI diagrams with source details. | **Do not promise to recreate** exhaustive packet-forwarding model. Support API/read-only snapshot comparison if enterprise already uses it; use its UX as quality benchmark for map/path confidence and discovery history. | Complement with streaming evidence and open, least-privilege network evidence APIs; verify claims rather than selling parity. |
| **Forward Enterprise (commercial)** | Queryable network digital twin, path search, config diffs, verification and snapshot-aware AI; commercial verification depth. | Consider limited read connector/snapshot oracle and comparison tests. **Don't clone network-wide symbolic forwarding** in the first roadmap. | Differentiate only with measurable transparent source provenance, streaming gaps and local/third-party agent safety. |
| **NetBrain (commercial)** | Automatic discovery, dynamic maps and troubleshooting driven by network context/automation. | Copy the useful journey principle (task-targeted topology view), not the product UI. Connect to external CMDB/ticket systems instead of duplicating them. | Scoped, replayable observations and deterministic, independently validated investigation evidence. |
| **Batfish (OSS)** | Offline vendor-config analysis, packet forwarding/reachability, differential snapshots, EVPN/VXLAN and policy verification questions. | **Evaluate integration as an optional independent change-assurance oracle** for supported NOS/config snapshots and legal licenses; do not rebuild parser and symbolic dataplane in Bonsai. Label Batfish *modeled* results distinct from live device/FIB observations. | Correlate modeled intent/diffs with BMP + live telemetry and expose disagreements safely to operators and LLMs. |

### Existing SuzieQ decision must be respected

`docs/architecture/adr_suzieq_vs_pyats.md` already evaluated SuzieQ versus Genie/TextFSM and decided SuzieQ **deferred** as a primary collector. The new action is a timeboxed **read-only adapter and side-by-side evaluation**, not a reversal of that ADR or a full SuzieQ deployment. First determine whether its vendor/namespace/time schema materially fills a demonstrated collection gap better than the current sidecar.

**Differentiation cannot be a slogan.** The measurable product promise should be:

> A vendor-neutral, evidence-bound network observation and operations layer that reconciles optional sources of truth with streaming control-plane and forwarding observations, reports known/unknown/conflicted states explicitly, and provides deterministic scoped evidence/assurance to human and AI operators.

To claim that product advantage, compare **identical lab faults and questions** (time-to-discover, conflicting-identity handling, freshness, on/offline source coverage, historical path evidence, false link rate, operator resolution time, resource cost) with SuzieQ and, where legally accessible, external product APIs. An honest "not supported" or "unproven" is better than fabricated parity.

## E. Acceptance scenarios and metrics

The backlog below is deliberately *test-first*. Required independent oracles and negative cases are part of acceptance, not optional UI polish.

|---|---|---|---|

## F. Bound backlog placement and implementation order

**No new top-level BN:** the canonical backlog already owns onboarding (BN-015), source identity/provenance (BN-008/021), topology completeness (BN-016), workflows (BN-013), auth/security (BN-020/022) and release/UI verification (BN-019). Add uniquely identified **bounded UI sub-slices** under those owners; avoid writing another UI redesign backlog.

**Slice 1 — correctness first:** BN-015-U1 NetBox contract; BN-015-U2 site hierarchy mutation; BN-016-U1 exact peer edge; BN-015-U3 canonical site identity. Add red tests; do not bundle with broad UI visual redesign.

**Slice 2 — capability-aware asset lifecycle:** BN-015-U4 no-gNMI and import modes; BN-015-U5 profile scope and mixed protocol plan; BN-015-U6 external SoT and CMDB conflict preview; BN-020-U1 setup/auth state.

**Slice 3 — honest topology contract:** BN-016-U2 inventory/observed merge, site subtree and off-site stubs; BN-016-U3 link provenance, layers and as-of; BN-016-U4 performance/rate semantics. Feed this contract to BN-013 evidence journeys.

**Slice 4 — polish and product comparison:** BN-013-U1 unified evidence journey; BN-019-U1 route/a11y/e2e/performance; BN-015-U7 timeboxed SuzieQ/NetBox/Batfish comparative adapter spike and capability matrix. Record decisions and keep rejected integrations rejected.

**Do not confuse acceptance with implementation:** this document contains source-based findings and proposed tests only. No UI/server code or runtime tests were executed. The release and support matrix must remain conditional until the above are demonstrated on genuine environments.
