# Cisco network-operations UI research — Hyperfabric, Nexus Dashboard, Meraki, Crosswork and WAE

**Date:** 22 November 2026 · **Status:** public research, comparative UI design input and actionable backlog intake; NOT shipped Bonsai code, validated parity, a verified deployment, or permission to reproduce vendor media. **Canonical work owner:** [BN-030 in BONSAI_BACKLOG.md](../../BONSAI_BACKLOG.md). **Related direct-video study:** [SkyCMD demo audit](SKYCMD_VERIFIED_VIDEO_UI_AUDIT_2026-11-22.md) and [initial cross-vendor workbench analysis](NETWORK_OPERATIONS_UI_RESEARCH_2026-11-22.md).

This document publishes the *textual* research and source references so future Bonsai maintainers and Devin can retrieve it with the normal repository. It intentionally excludes downloaded proprietary screenshots, video recordings, transcriptions, and local-workstation migration instructions. External image and video URLs belong to their respective owners and may change.

## Method: separate what the source actually showed from conclusions

- **S — inspected official still:** UI was examined in a Cisco documentation image or a Cisco-hosted video **chapter thumbnail**. The thumbnail is one captured scene, not evidence of the entire recorded interaction. Some chapter thumbnails are presentation slides, not live product UI.
- **T — indexed video chapters or transcript:** the official product tutorial or indexed chapter headings describe a workflow; the complete hosted video was **not played frame-by-frame** here. Chapter timestamps below refer to that chapter index, not locally viewed moments.
- **P — product manual:** the vendor documentation describes a capability, without independent production proof.
- **I — Bonsai design inference:** recommendation that follows from S/T/P, *not* proof that Cisco or Bonsai already implements it.
- **SkyCMD comparator:** in contrast, the user-provided 127.63-second SkyCMD MP4 was played and timestamped in the linked audit, but its AI pane visibly states `DEMO DATA · SIMULATED FABRIC · DEMO AI RESPONSE`. Do not claim real GPU-job degradation, production AI safety or real ECMP forwarding from that demo.

The analysis avoids fabricated click flows, observed latencies, benchmark claims and screenshots. Keep source-version/date alongside any future research refresh; products and terminology evolve.

## Executive design conclusions

Cisco presents several complementary *operational objects*, not one universal view:

| Product/era | Primary operator object and visual strengths | Adoption for Bonsai | Critical evidence distinction |
|---|---|---|---|
| **Nexus Hyperfabric** | Designed/claimed/installed fabric; device faceplate, physical cabling, port assertions, on-site task steps | Planned-vs-observed infrastructure, verified LLDP relationships, physical port grid with explicit status | An assertion or planned cable is not verified link/traffic health |
| **Nexus Dashboard** | Fabric inventory, topology, operator-specific overlays, fault/anomaly correlation, history, pre-change analysis | One shared topology with control-plane/operational/evidence perspectives and ranked anomalies | Root/correlated relationship is not automatically proven causation |
| **Meraki Dashboard** | Device/client 360, historical connectivity events, failure phase and attachment context | Treat client session/onboarding as first-class investigation, including campus wired/wireless | DHCP failure, RF retries and TCP retransmissions are different layers |
| **Crosswork Network Controller/Assurance** | Service/transport as entity, VPN assurance dependency graph, probe vantages, tunnel/path | Service-to-component evidence tree and time-scoped SLA journey across P/PE/CE/VRF/LSP/SRv6 | Contract/service dependencies alone are not observed forwarding paths |
| **Crosswork Workflow Manager** | Explicit workflow job phases, evidence and upgrade/config validation | Progress/receipt model for *read-only* cases, inventory reconciliation and centrally authorized collector changes | Do not authorize device CLI/config writes by copying vendor controls |
| **WAE Design → Crosswork Planning** | Traffic demand models, TE/path, worst-case resource planning, failed node/circuit/SRLG simulations | Future separate read-only What-If/Impact Workbench against versioned network baselines | Predicted/simulated utilization must NEVER be painted as measured live utilization |

**Lifecycle verification:** Cisco's published [WAE EOL notice](https://www.cisco.com/c/en/us/products/collateral/routers/wan-automation-engine/wan-automation-engine-eol.html) presents **Crosswork Planning** as the replacement/migration direction for the retiring WAE. The current [Crosswork Planning 7.2 network simulations documentation](https://www.cisco.com/c/en/us/td/docs/cloud-systems-management/crosswork-planning/7-2/design-guide/cisco-crosswork-planning-design-user-guide-7-2/simulation-overview/network-simulations.html), [failure-impact view](https://www.cisco.com/c/en/us/td/docs/cloud-systems-management/crosswork-planning/7-2/design-guide/cisco-crosswork-planning-design-user-guide-7-2/evaluate-impact-of-worst-case-failures/failure-impact-view.html) and [simulation analysis tool](https://www.cisco.com/c/en/us/td/docs/cloud-systems-management/crosswork-planning/7-2/design-guide/cisco-crosswork-planning-design-user-guide-7-2/evaluate-impact-of-worst-case-failures/simulation-analysis.html) describe failure consequences, worst-case utilization and reconvergence modes. Older WAE UI remains historical inspiration, not a current-release screenshot of Crosswork.

## Architecture implications: extend existing Bonsai UI rather than clone vendors

### 1. Shared investigation shell (BN-030-01..05)
Use one tenant-authorized view context: site, fabric, VRF/SSID/service/client, selected link/port/queue/path, incident, time `as-of`, comparison period, observation vantage, authority, source coverage and evidence IDs. Navigation from Live → DeviceDrawer → Routing → Investigations → metrics history must preserve time/scope and support link sharing with RBAC. Investigate/Explore/History/Overview primary navigation with administrative functions still accessible; resolve existing sidebar/CommandPalette shortcut mismatch and test real browser history.

### 2. Physical + lifecycle truth (BN-030-09/15 and new BN-030-19)
Combine Hyperfabric's port grid/cabling plan with SkyCMD's metric-selected switch faceplate. Interface mapping must come from trusted model/NOS identity, cage/port breakout and discovered attachments; use a generic grid when unknown. Separate proposed cabling, accepted inventory, known installed state, observed LLDP and independent working link. “Unobserved,” “missing,” “stale,” “rejected assertion,” and “healthy” each need distinct labels, intervals and provenance. Show a modern assertion status card, but do not grant network writes.

### 3. Correlated anomaly + timeline (BN-030-05/10/17 and new BN-030-20)
Nexus Dashboard's conceptual root event, secondary anomaly and impact presentation can be built atop Bonsai's existing observations, investigation cases and graph. Show what was actually observed vs correlated by time vs hypothesized causal edge; annotate conflicting or missing probes. Guard against collector partition, clock skew, stale evidence and topology bias. Distinguish a device/syslog event from a service health regression or a user-perceived problem. Do not duplicate the inference engine or introduce a free-form raw SQL endpoint.

### 4. Campus client 360 (BN-030-08 and new BN-030-21)
Meraki's client session view reduces operator work because it organizes problems by *client journey*. Model association, EAP/RADIUS authorization, DHCP lease, DNS, network reachability and app connectivity as independent observed stages. Show main and related event summaries, selected historical interval, Back to Current, attachment topology, Wi-Fi radio/SSID/channel, switch access port, PoE/NAC, and source/cadence. State “not instrumented” when RADIUS/DHCP/endpoint data is absent, never manufacture success. Pseudonymize client identity; protect records with tenant and field-level ACL.

### 5. Service/transport assurance tree (BN-030-04/07/16 and new BN-030-22)
Crosswork's service dependency view suggests a bounded, collapsible hierarchy: customer/service → PE/VRF/VPN/EVPN → overlay/tunnel/LSP/SR policy → supporting interfaces and QoS → SLA/probes. Each edge is typed (configured, claimed, observed, candidate, measured) with provenance; missing topology is not proof of missing service. Probe vantages, time ranges and verification status are critical. Down-and-degraded-only filter must not silently hide unknown instrumentation; show evidence and denominator. Never claim actual ECMP forwarding solely from LLDP, IGP or RIB.

### 6. **Independent read-only Planning/Impact Workbench** (P2; new BN-030-23)
The genuinely new UI capability is a *separate simulation layer*, informed by WAE Design and Crosswork Planning. Start with a versioned, bounded baseline: approved network snapshot, traffic demands with origin/confidence, circuits and costs, capacities, LAG/SRLG/site failures, path/TE and ECMP assumptions, QoS, N-1 scenarios and clear model freshness. A candidate failure creates a scoped, sandboxed **simulation job** that returns modeled path changes, links at risk, predicted utilization and capacity hotspots, plus uncertainty or unsupported scenarios. Side-by-side `measured`, `candidate`, `simulated`, `worst case` columns and legends; distinct palettes for planned vs live. There is **no apply/remediate button**, no writeable device API, no operator-equivalent source of topology truth, no mandatory external licensed simulator or database. Export evidence and scenario assumptions. Later consider N-2, reconvergence phases, SRv6/LSP and independent probe validation only after correctness is established.

**Performance gates:** cap node/link count, scenario combinations, worker memory/CPU/time, requests per tenant, generated graphs and export size; cancellation and cache invalidation after baseline change. L0 unit fixtures for capacity/failed SRLG; L1 integration reproduces known demand redistribution; L2 browser screenshot assertions for model badge; L3 independent test with known real traffic/forwarding; never assert algorithmic parity to Cisco without real proof. A predicted outage is not a current incident.

### 7. Job/receipt presentation (new BN-030-24)
Crosswork Workflow Manager's task stages fit read-only investigations, acquisition readiness checks and collector rollout approvals. Bonsai uses its existing authenticated Core task orchestration and policies: queued → validating → running → verified / failed / canceled; show actor, scope, versioned plan, command/tool type, permitted inputs, timestamps, source receipts, eventual cancellation, revocation and audit trail. Keep current operational device-write ban. Avoid unscoped `Apply`, `Reconfigure`, or `Disable port` actions borrowed from Cisco examples.

### 8. One shared design system (BN-030-11/12; no new product-specific UI islands)
Both bright dashboards and dark fabric devices in screenshots are visual references, not a color specification. Preserve existing Bonsai design tokens, define *semantic* states measured/declared/inferred/simulated/unknown/denied, ensure accessibility beyond color-only legend, non-blinking alert refresh, responsive 390/1024/1440, keyboard+screen-reader alternate path lists and graph summaries. Prefer compact tabular evidence to impossible 10k-node hairballs. Progressive data queries, virtualization, bounded SSE and no browser-routed direct database queries.

## Golden acceptance journeys to add to UX evidence corpus

| Scenario | Minimum expected user journey | Trap and negative test |
|---|---|---|
| AI congestion | Port faceplate → PFC direction/priority → queue → selected path(s) → authorized workload evidence → evidence-based investigator | LLDP candidate path and PFC alone cannot prove GPU rank slowdown |
| Incorrect cabling | Planned link → expected A/B transceiver/port → observed LLDP → mismatch or unknown assertion → audit | Missing observation ≠ disconnected or cable incorrectly installed |
| Intermittent app | Time-aligned flow/port incidents → alternative hypothesis + source coverage | Correlation ≠ cause, NetFlow ≠ TCP cwnd |
| Pre-change | Approved observed snapshot → model candidate → diff and confidence → non-executable report | Candidate changes never appear as applied |
| Campus DHCP failure | Client session → failed onboarding stage → AP/access switch/DHCP chain → historic/current comparison | A DHCP failure must not be labeled RF interference |
| Campus roaming and WAN | RF MAC retries vs TCP retransmissions; uplink vs WAN probe | Distinct observation layers and denied client data |
| SP L3VPN SLA | VPN → subservices → PE/VRF/LSP → independent probe vantages | Service dependency != verified path |
| SR/RSVP path utilization | Measured vs candidate/simulated path, demand sources, queue data | Model routing may differ from actual forwarding |
| Circuit failure what-if | N-1 circuit/SRLG simulation → projected hotspots vs measured baseline → assumptions | Never recolor live map or trigger actual config |
| Dark site | Collector status vs network path vs OOB and facility signals | Telemetry partition ≠ power loss |
| Diagnostic workflow | Scoped, versioned read-only job → receipts, retries, cancellation, RBAC | No CLI/SQL prompt injection or device writes |
| Agent root cause | Root/correlated events → counterevidence → caveat → cited output, abstention | Simulated AI demonstration ≠ production proof |

## Delivery and non-goals

**P0 before visual innovation:** corrected nav/shortcuts and temporal truth (BN-030-01/02). **P1 vertical implementation:** shared scope plus one real port incident (03–06, 09–10, 15–17), Meraki-style client journey and Crosswork service view (21–22), anomaly evidence and lifecycle assertions (19–20), read-only workflow receipts (24). **P2:** independently gated what-if planning (23) only after telemetry, trust, graph and demand sources are proven. All changes must reconcile with BN-013/015/019/024/025/026/027/028/029 and current M6/Secure Core gates. No duplicate graph, metrics store, agent authority or expensive monolithic redesign.

**Research extensions, unverified visually here:** Arista CloudVision Time Machine / Change Control, Juniper Mist/Marvis wired/wireless root cause, HPE Aruba Central client UX, Nokia NSP layered service graph, NetBrain dynamic path doctor. Their source leads are included in the tutorial catalogue; do not treat them as reviewed screen interactions.

**Maintainer workflow:** consult this report before implementing BN-030 or commissioning new competitive UI research. Keep source URLs/timecodes/release identifiers and explicit S/T/P/I evidence per observation. Update the canonical backlog with owner, acceptance, real validation and security context. Text-only analysis belongs in normal Git documentation; do not publish proprietary vendor video/still binaries or uncontrolled real customer data.
