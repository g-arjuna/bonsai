## Visual system / controls seen (not speculative)

- **Palette:** predominantly very light cool-gray/white page surfaces; charcoal/navy device-faceplate panel; pastel-to-saturated blue port traffic fill; green for passing/healthy, amber for congestion, red accent for drops/lost traffic; thin gray separators and very little decoration. Bonsai may retain its dark palette; copy *semantic hierarchy*, not branding.
- **Hierarchy:** top line compact global shell, second-level selected device and multi-domain health bar, tertiary chip/toggle controls, spatial map/faceplate centre, detailed facts and chart below. Expanded AI findings consume the main canvas with a related contextual right rail. Direct “Show on map”/“Investigate” buttons eliminate unscoped navigation.
- **Data density:** the map is dense even in a 1280px marketing view. Compact typography and many icons/small labels can be hard to read, while path rows provide a more accessible alternative to following crossing fibers. Bonsai should test ≥1440 / 1024 / phone widths, zoom, keyboard path selection, screen-reader table equivalence, contrast and larger-text mode.
- **State:** liveness is explicitly labeled with last update, ports have color-by semantics and metric source identity; severe incidents are amber/red scoped, not giant unconditional global alarms. Separate metrics that measure ongoing counters, events, host reported state and topology declarations.
- **Interaction/ergonomics:** exactly 15min/1h/6h/24h presets seen, Fit / Full size and Hosts toggle, selected endpoint chips, ranked affected port lists, precise per-interface actions, analysis “Copy brief”, mobile follow-up text field. Some are genuinely visible, others (e.g. no full running export) cannot be inferred.

## What the video **does not prove** — keep our product evidence stronger

1. **Simulated data**: demonstrator visibly labels simulated fabric and AI response. No proof of underlying deployment security, performance, availability, scale, live AI verdict quality or real switch hardware.
2. **GPU impact**: Map includes host names resembling GPU endpoints and “all GPUs” messaging; no independently measured NCCL/collective/job step degradation or scheduler join is demonstrated. Do not claim a link incident affected every GPU. Bonsai BN-025/030 must require trustworthy app/rank membership and time-aligned workload evidence before asserting blast radius.
3. **Path semantics:** “64+ paths” and “one of six” are enumerated topology alternatives, not verified production ECMP hash selections or actual forward/reverse data-plane paths. Distinguish physically connected and candidate from observed forwarding/probe.
4. **Microburst precision:** 10ms “Burst scope” is a UI affordance, not proof of sensor capabilities, interval coverage or backend storage costs.
5. **LLM/AI security:** “read-only SELECT 25s” is on-screen behavior/text in *demo AI response*; not independently proven sandboxing/tenant authorization/timeouts or redaction.
6. **Mobile support:** portrait scenes show design, not independent device/browser runs with real network latency or accessibility audits.
7. **Observation vs explanation:** cause-card suggestions are not independent controlled-truth labels. “ECMP hashing/capacity” is hypothesis; explicit competing alternatives and counterevidence remain required for Bonsai.

## Detailed design recommendations for a Bonsai first-class experience

**Hero operator journey (AI fabric)**: scoped AI pod → alert “egress tail-drop on leaf port 59/1” → select **congested candidate path** and see unaffected alternatives (not all ranks) → device panel header identity/collector/last-good → exact physical port or semantic port grid → choose “PFC per priority”, “ECN marks”, “queue occupancy”, “tail drops” and compare in/out with reset/clock/coverage → time-brushed chart and packet/port event panel → assistant investigates with bounded tool receipts, cites evidence and counterevidence → share scoped redacted case; no blind tuning or device writes.

**Same component pattern, different metrics:** SP path viewer shows P/PE/CE/LSP/VRF/policer, RTT and independently observed TCP retrans/windows; campus viewer shows AP/radio/SSID/access-port/PoE/RADIUS and differentiates RF MAC retries from TCP. A physical switch faceplate is optional here (router/line-card or AP radio grid alternative). Never graft RoCE/PFC-specific counters onto a device that does not expose them.

**Performance/quality gates:** (a) 66-port realistic faceplate viewport and port tooltip render; (b) adaptive orientation/port-lane display and no per-vendor manual hardcoded hacks; (c) metric color-by legend + absence hatch and sample age, no fake “blue healthy”; (d) 1k/10k candidate topology scale with bounded grouping and path pagination (not line hairball); (e) 5-second bucket and optional 10-ms burst zoom only when source supplies data, profile bandwidth, backpressure, rounding and retention; (f) changed-scope time races, auth revocation, screen reader and p95 interaction targets; (g) trace preserves selected endpoint, candidate-path provenance and incident time; (h) simulated AI response *never* passes as real provider acceptance.

### Sequencing recommendation

Do **not** redesign all 27 routes. First fix canonical shortcuts and time/freshness; then one real data-backed **leaf port investigation**: DeviceDrawer semantic faceplate or fallback, PFC/drop metric selector, annotated time series, specific port/drop event card, alternative paths with truth badges, and grounded read-only investigation panel. Follow with path visualization and mobile workflow, then service-provider and campus reuse. Implement as additions to existing BN-030 and current BN-025/026/027/024/013 owners, not a parallel UI/product or second telemetry store.
