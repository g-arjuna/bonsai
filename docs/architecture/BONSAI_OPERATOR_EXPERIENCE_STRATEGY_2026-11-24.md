## 1. Product thesis and decisions

Bonsai is a continuous, evidence-backed network operations workbench, not a generic dashboard, vendor controller, graph editor or chatbot. Its UI must answer: what is affected, what changed, what can we actually see, what does Bonsai understand, what remains unknown, and what is the next safe check? At every level an operator can drill down to exact entity, time, scope, source, interpretation revision and evidence. An honest gap is useful operational information, not a failure to hide.

Keep Svelte 5, current Core APIs, D3 where suitable, existing token/density foundations, YANG workspace, routing service and existing routes while migrating workflows incrementally. One authorization boundary, canonical identities, time/scope context and evidence model shared by UI/API/MCP; no second graph, browser-side topology inference, independent role authority, additional metric store, separate incident execution path or mandatory proprietary UI library. Device writes remain disabled. UI actions change Bonsai's approved collection/configuration or execute separately authorized read-only diagnostic jobs, never live device config.

**Co-delivery:** new operator-facing backend features are incomplete as a user capability unless their exposure, failure/unknown states, source and verification path are defined and demonstrated. A pure parser/ABI/research slice may land offline with an explicit deferred surface, owner and dependency; it is not promoted as an operational feature. Do not halt an active trusted gate to redesign the UI, and do not force a full UI build for each pure algorithm test. Implement frontend/backend vertical slices once the contract is stable.

### Operator jobs rather than protocol menus

- NOC: see actionable issues, ownership, affected services, timeline and next check; follow an incident without losing scope.
- Network engineer: inspect interfaces, configuration semantics, routes/VRFs, LSPs, overlay membership, counters, paths and source evidence; compare times.
- Platform operator: see discovery, acquisition, collector health, queue/replay, parser/semantic gaps, retention and job failures; repair Bonsai's visibility.
- Assurance/planning engineer: compare intended/effective/observed/validated states and bounded modelled scenarios; never confuse simulations with measurements.
- Security/reviewer: scope access, inspect decisions and redacted evidence, adjudicate findings and approve authorized Bonsai operations.
- AI/ML operator: know if usable data, baseline, feature and model exist for this exact subject; understand why an inference is withheld or stale. Keep advanced BonPy configuration and model tooling available.

## 3. Information architecture and canonical object workbench

Proposed stable primary tasks (labels to validate with operators): **Overview**, **Network**, **Assurance**, **Incidents**, **Investigate**, **Data & Coverage**; grouped **Administration** (inventory/onboarding, collectors, source policies, integrations, access, approvals, jobs, retention, system). Existing routing/RIB, event/history, configuration, explorer and BonPy remain reachable through context, search and deep links. Do not remove functionality or expose unauthorized object counts via hidden navigation.

Global context bar: authorized organization/tenant/environment → site/fabric/service, live vs as-of range, time zone, source health/coverage, search, active investigation. Preserve selected object, filters and snapshot across map ↔ table ↔ drawer ↔ investigation, browser back/forward, reload and safe share. URLs carry scoped stable IDs or opaque handles, never credentials, raw configs or cross-scope cached responses. Scope/time are validated on the server. Local preferences are non-sensitive and per principal; logout/scope revocation invalidates private data.

Overview answers “what needs attention?” with separate open incidents, affected services, visibility gaps, stale sources, recent meaningful changes, baseline/model gaps. No giant wall of KPI cards. A small summary row, ranked actionable list and scoped map/table. Empty setup shows next onboarding step; healthy with complete evidence is distinct from not yet observed.

The common object page template is **Overview / Relationships / State & Metrics / Config & Intent / History & Events / Evidence & Coverage** (illustrative, not six required tabs for every entity). Header: scoped identity, role(s), platform/release/ASIC, lifecycle and latest observation; contextual panels for selected issue. Expand to full detail as needed. UI routes are organized by operator object and task, not one new top-level page per parser/protocol.

Objects: environment/site, device, chassis/line card/port/lane, LAG/member/subinterface, routing instance/VRF, tenant/service/VPN/VNI, adjacency/session, route/path/candidate/LSP/SID, PCE/controller, queue/priority, AP/radio/client session, circuit/OOB/power, collector/source, config revision, baseline/model, event/alarm/incident, evidence/task. Use shared object references, not mandatory graph node for every sample or opaque parser token.

### Adaptive composition, not device typecasting

A device may be border leaf + route reflector + WAN edge; a site may contain campus and DC. Role is a many-valued, scoped and provenance-bearing attribute, not a rendering type or collection authority. Feature modules are contextual panels defined by a versioned presentation contract referencing the existing BN-024 feature registry and M6 applicability. No second platform registry. Detect applicable feature through trusted inventory/config/model/operational evidence. A hint can suggest a feature, but not establish semantics. Panel states: applicable/observed, configured-only, observed-only, partial, unsupported, not collected, stale, conflict, unknown, denied, disabled. Explicit not applicable may be collapsed; unknown is discoverable in Coverage. Keep a stable shell, avoid navigation churn as telemetry updates. If a tenant is unobservable, do not hide a missing-coverage warning merely because an overlay panel is not promoted. Unauthorized feature details are not leaked by counts or hints.

## 4. Visibility and understanding are first-class product objects

One **Data & Coverage** workbench plus contextual Coverage panels everywhere. Extend existing registry, device schema/acquisition, routing coverage, BN-024 typed facts, feature manifests and source health; do not invent evidence from labels. Stages are independent axes, not a linear progress bar implying all devices use gNMI:
1. Declared/registered identity, authorized scope, credential binding.
2. Discovered platform/version and capabilities, schema/feature applicability.
3. Selected/approved acquisition, assigned to collector, submitted/applied, initial sync, source-specific checkpoint and freshness.
4. Raw evidence captured, extraction outcomes, normalization, semantic resolution, config/operational reconciliation.
5. Validity and coverage, usable historical series, baseline eligibility/readiness, model applicability/validation.
6. Graph projection checkpoint, independently verified assessment, operator/agent visibility.

Per device and per feature render state, last successful stage, reason code and plain-language explanation, expected cadence, last attempt, last observation, current config/plan/schema/parser/model revision, source and exact allowed action (e.g. retry discovery, re-preview plan, request approved read-only capture, inspect gap, export redacted evidence, report missing parser support). Configuration capture may succeed while parsing fails, or parse succeeds while effective semantics are incomplete. A passive BMP device is not required to pass gNMI; no automatic stage promotion.

### Coverage denominators (no arbitrary “Bonsai understands 70%”)

Define a versioned feature requirement set (per platform/release/role/feature/scope) with explicit required/optional/applicable/not applicable/unknown/unsupported elements, source and revision. Show counts at each stage, not one blended score. Distinguish **implementation coverage** (qualified functionality in this Bonsai version), **device semantic coverage** (supported applicable clauses/elements in a particular snapshot), **observation coverage** (required metrics/fields/entities seen fresh for a window), **collection continuity** (expected vs received sample windows, gap/reset), **baseline readiness** (per metric/time window prerequisites) and **independent validation**. No cross-device or cross-feature aggregation without compatible denominator, same policy and coverage window. Required missing/unsupported stay in denominator when known; excluded, optional and unresolved applicability counted separately. If total unknown, display known lower bound or unknown with missing scope; 0/0 = not applicable or unknown, never 100%. Counts of syntax lines, parser success, paths advertised, samples, configured statements and effective semantics are not interchangeable. Weight only explicitly defined reviewed requirement sets; no arbitrary LLM confidence percentages. ACLs apply before aggregation.

When a new SR-PCE-related config statement is not understood, preserve source span and a typed diagnostic; if reliable lexical/structured evidence suggests PCEP, show a **candidate feature** and explain what is not supported. If even classification is unknown, display an unclassified statement with context, not pretend to recognize the controller. Group diagnostics by stable feature/revision/reason, occurrence count, first/last seen, affected authorized devices; link to parser/version, safe sanitized sample and issue-report workflow. Avoid creating a network fault alarm for every unhandled syntax node. A new config revision invalidates affected effective coverage; stale previous facts remain as historical evidence.

Coverage workbench views: per-device lifecycle, feature matrix across platform/releases, failed/stale source jobs, unclassified config and unsupported features, unresolved identity/link mapping, collection gaps/replay and baseline gaps. Filters by site/tenant/feature/NOS/version/collector, reason and age, bulk safe retry through existing approved job API where allowed, no device writes. Unknown remains visible even if domain view is not promoted.

### Feature exposure contract and delivery checklist

Every operator-facing slice declares stable feature ID/version, owning backend contract and schema, source/plane, applicability and requirement-set version, stable object refs, authorized scope, time/coverage/reason codes, supported query/actions, primary surface, contextual drilldown and diagnostics fallback, safe redaction, stale/error/empty/unsupported examples and acceptance fixture. Derive capabilities from existing authoritative metadata; one checked UI mapping inventory, not a parallel policy engine. The browser consumes typed domain values, not arbitrary user-defined HTML or a graph schema renderer. Use shared primitives for state chips, evidence links, tables, metric charts, receipts and coverage; custom domain visualization only where needed. Track each backend field class as surfaced, contextual, deliberately internal (security/high cardinality), or deferred with owner/reason. Raw secrets never exposed by a “show all data” escape hatch.

## 5. Canvas and network navigation architecture

Use one scoped typed multigraph projection, separate from layout. Entities and edges retain stable canonical IDs, direction, layer, endpoint/interface/VRF/AFI/namespace, provenance, validity and confidence/authority. Layout is a view preference, not a claim about actual role or physical adjacency. Offer auto (general graph with optional clustering), user-pinned/free layout, explicit hierarchy (only where meaningful), geographic/site, fabric/pod/rack, service/path and dependency perspectives. Choose layout using topology evidence and operator selection; label heuristic placement, persist per-user/scope/layout pins; don't jump when health changes. Preserve filtered cross-boundary stubs and hidden-member counts; don't imply link disappears because scope filter hides it.

Physical layer: individual ports, breakouts, LAG and member links. Logical layer: parent/subinterface/VLAN/VRF/network-instance with service attachments. Underlay/control plane: IS-IS/OSPF/BGP/BFD, directional topology/metric. Overlay: VTEP/EVPN/VNI/VRF, route/RT membership. Transport: LSP/SR policy/candidate/PCE dependency; forwarding: installed/software vs validated paths; dependency: circuits/OOB/power/collectors/tenant services. One active metric legend and explicit units/direction/time; don't paint cumulative octets as load or reserved bandwidth as traffic. Use parallel edge lanes for small selections and explicit bundles for dense views, preserving members and exact IDs for highlighting. Show unknown/half-discovered/stale links as distinct dashed/hatch patterns, not green. Search/pin, fit selected incident/path, expand group, compare alternative paths side-by-side, selectable rows and matching map highlight. Provide keyboard-accessible equivalent entity/link list, not SVG-only interaction.

Acceptance fixtures: mixed DC border leaf with external peer, RR not on data path, redundant spine/leaf with parallel ports and LAG, routed subinterfaces with multiple VRFs and overlapping addresses, ring/mesh SP, campus plus WAN, standalone device, partial/unresolved identity and cross-boundary connection. Test stable positions on metric-only refresh, empty filter, wrong tenant, path highlighting one exact member, grouped zoom, narrow viewport and measured scale; do not make browser infer relationships from hostname, management IP, degree or device type.

## 6. Alerts, events, alarms and incidents: reduce noise without hiding facts

Current `group_into_incidents` is a priority correctness issue: two unrelated faults in the same time window can be grouped even if no scoped shared entity or dependency exists; root-degree and rule-name heuristics produce unjustified causal language. Time is a candidate retrieval bound, not correlation proof. At immediate correction, describe legacy grouping as temporal candidates, root unverified, and remove claims unsupported by evidence; keep previous IDs/evidence link compatibility with explicit version/migration. Full correlation is separate bounded work with BN-013.

Inspiration (public source/documentation, not drop-in dependencies):
- [Prometheus Alertmanager grouping and inhibition](https://prometheus.io/docs/alerting/latest/alertmanager/) and current source [dispatch/dispatch.go](https://github.com/prometheus/alertmanager/blob/main/dispatch/dispatch.go) (`getGroupLabels`, `groupAlert`, fingerprint, timer) and [inhibit/inhibit.go](https://github.com/prometheus/alertmanager/blob/main/inhibit/inhibit.go) (source/target matchers, equal label cache, mutedBy). Observed grouping and inhibition are notification/routing semantics, not network root-cause inference.
- [OpenNMS Horizon alarm reduction and clear keys](https://docs.opennms.com/horizon/latest/operation/deep-dive/alarms/configuring-alarms.html): event-to-alarm lifecycle, stable resource-specific reduction identity and matching clear; avoid broad nodeUp clearing unrelated faults.
- [Zabbix global event correlation](https://www.zabbix.com/documentation/current/en/manual/events/event_correlation/global): explicit old/new event tags and pair conditions; broad close rule is dangerous.
- [Grafana alerting notification grouping](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/): grouping intervals, instance list and notification policies; [inhibition](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/inhibition-rules/) distinct from silence.
Pin immutable upstream versions, review source/licensing and implementation details before any reuse. No need for new production Alertmanager/OpenNMS/Zabbix dependencies.

Target separation:

    durable raw event / sample → typed signal/detection
           → exact alarm identity and repeat/clear lifecycle
           → bounded correlation candidates with typed dependency evidence
           → versioned incident / possible cause / measured impact
           → triage, ack, ownership, notification/silence policy
           → investigation and independently adjudicated outcome

Exact alarm reduction keys include tenant/environment, canonical device, resource/interface or peer/view/VRF/AFI, condition and applicable source/epoch; preserve individual raw event refs, dedup only with proven identity, stable incident ID independent of current root candidate. A clear must match exact resource/condition and valid lifecycle/epoch; silence inhibits notification, ack acknowledges, neither asserts resolution. For cross-protocol correlation use resolved interface/peer dependency, source independence/fate-sharing, direction, clock uncertainty and causal mechanism; require corroboration and keep contradictions. Use bounded candidate index by scoped entity/time/dependency, not global O(n²) over all events. Missing labels/identity never merge by empty equality. Scope filter before counts/search. No untrusted text or embedding similarity alone proves cause. Preserve raw events and explain membership/rule versions; replay out-of-order/duplicate/late and partial evidence, support split/merge/adjudication audit and revoke stale hypothesis. Reuse existing journals/graph/write coordinator and existing retention; no second alert authority. Distinguish operator-facing network alarms from collection gaps and model diagnostics.

Example: SNMP linkDown on PE-07 interface X, gNMI oper down on same scoped interface, BMP session down whose next-hop actually depends on X, and syslog on unrelated PE-09 in same second. First two may reduce/corroborate one interface condition; BMP is a related symptom only after dependency evidence; PE-09 stays separate. Shared collector loss is visibility outage, not all devices down. Recovered interface doesn't automatically resolve BGP or service outage. Show hypothesis, witness, counterexample, gap, true/possible impact separately.

**UI:** dedicated Incidents triage table (open, severity, age, owner, scope, affected service, corroboration, state), grouped alarms with repeat count and first/last seen, expandable raw event stream and synchronized timeline, not a giant unfiltered ticker. Faceted server-side filters: tenant/site/device/resource/role, source/protocol, severity, condition/event type, lifecycle/ack/suppressed, time, incident ID, feature, service/VRF, freshness/trust, correlation status, search text. Saved authorized views, clear all, counts/denominators, stable sort/paging/cursor, pause display and show new-event count, resume catchup or explicit gap, history retention boundary. Explain why grouped, why hidden from notification, why cleared, link evidence and safe investigation. No silent auto-dismiss or false “nothing happened.” Time range/scope shared with graph and detail. Export only authorized/redacted bounded results.

## 8. Visual language, accessibility and responsive behavior

Aim for a calm, technical, editorial operations console: prioritize data density and legibility; consistent alignment, flat surfaces, clear dividers, restrained typography, useful whitespace, not marketing dashboards. Avoid giant gradients, excessive rounded cards, decorative glow, emoji nav, rainbow charts, giant decorative metrics, gratuitous animations and generic AI summary boxes. Keep Bonsai brand teal for focus/selection/actions; use one coherent line icon set (lucide-svelte already a dependency), accessible text labels; domain icons convey function, not fixed physical tier. ## 9. Responsive data architecture and release checks

Common typed query result envelope: authorized scope/snapshot, state (idle/loading/refreshing/ready/empty/partial/stale/error/denied/unsupported), data, last success/observed time, source coverage/gap, reason/retryability, cursor, retention and evidence refs. Distinguish legitimate empty from failed fetch. Never keep cross-scope stale data. On scope/selection changes abort obsolete requests and fence responses by generation; key cache by principal/scope/feature/time/checkpoint and clear on logout/revocation. Coalesce poll/SSE invalidation; schedule from completion, bounded concurrency and backoff, stop when hidden/unmounted, reconcile snapshot and durable replay on reconnect, explicit lag markers. Use batched summary/read model when useful, server-side facets/cursors, virtualization and aggregated geometry; load heavy charts/graphs on demand. No browser-arbitrary Cypher/PromQL/shell or bypass Core auth. Measure query/ingest contention before adding read-model persistence. Keep actual telemetry source cadence visible; animation and UI refresh cannot improve underlying sampling.

Performance acceptance targets, not results: good [Core Web Vitals](https://web.dev/articles/vitals) reference LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at p75 representative conditions, plus BN-030-12 app-specific p95 selection <100ms, warm chart refresh <500ms, first useful bounded API view <1s target lab. Record hardware/browser, dataset, warm/cold, network, result bytes, requests/second, query CPU/RSS, writer/queue lag, FPS/long tasks and heap after navigation; 1k then 10k inventory/5k+ links and 20k aggregated clients, 100k event-history sample, event burst and slow source, 390/768/1024/1440/1920. These are staged synthetic scale targets, not physical lab proof. No fixed performance claim before measurements. Protect telemetry hot path from UI and ML queries. Fail fast with partial results and explain what is missing.

**Verification levels:** typed contract tests (state and scope), component tests with golden fixtures, real Core API/browser tests (not screenshot mock), staged load traces, independent real lab witness, operator workflow evaluation. Screenshots for every meaningful state, layout/contrast, no fake healthy defaults. Manual WCAG and real keyboard/touch. Golden journeys:
1. Imported offline device → credentials → discovery/applicability → approved/submitted/synced → native facts (or gap), schema revision invalidates approval, UI points to next step.
2. Config change contains unsupported PCEP syntax; old semantic facts stale; LSP state still fresh; coverage denominator/why/exact redacted span visible; PCE session not installed policy.
3. Mixed multi-role border leaf, multiple subinterfaces/VRFs, overlapping addresses, parallel physical links and one faulty member; selected tenant overlay and exact path do not bleed.
4. SNMP/gNMI/BMP correlated with dependency vs unrelated simultaneous fault; raw witnesses, stable alarm/incident ID, repeat/clear, split/adjudication, pause/reconnect gap.
5. Site blackout vs shared collector partition, cross-vantage evidence and OOB runbook with scope.

10. Read-only simulation vs observed view: separate model provenance/time and no Apply device write.
